# 资源与响应优化说明

版本：2026-10-17。适用于 Python 桌面程序及本次文件夹打包版；不涉及独立 web 或半导体提取程序。

目录维护注记（2026-10-22）：下文提到的历史 `_tmp_resource_qa/` 原始测量已随旧临时产物归档到 `<本机路径，不随源码分发>`，可恢复。测试命令会在原输出路径重新生成新测量；不要把新旧数据混作同一次实验。服务层整理未重新宣称或保证下列历史性能数字。

## 本次改变

1. 数值库默认单线程。程序的小规模数值运算不再默认唤起两套各 16 线程的 OpenBLAS 池，减少线程栈提交和竞争；只在本进程启动时设置，未修改系统环境、注册表或其他程序。
2. 隐藏图表不保留整幅像素缓冲。普通页面保留图元和数据，显示时重建；未访问的画布只分配极小的 Tk 图片。
3. 多路结果按视口绘制。功率级、器件损耗、电容页保留全部 OUT 及滚动高度，只为可见卡片创建完整画布，移出视口释放。滚动/缩放合并调度，每次回调最多新画一路；滚回需短暂重画，不能据此认为其他输出被删掉。
4. 限制快照缓存和邮箱。计算缓存同时受最多 3 项及估算 64 MiB 限制，按最近使用淘汰；超大结果仍正常计算与发布，不缓存。不再在空闲工作线程、旧页面或未读消息中额外保留上一代大波形。
5. 环路按需计算。拓扑首屏不预加载 `control`；首次进入⑤环路或⑩评审可能短暂显示加载提示。同参数只重复绘图，不重复求 Bode 数值；电气参数变化后使用新结果。依赖加载失败会停止轮询并显示原因。

缓存预算是对缓存对象和数组的估计，不包含 GUI 当前结果、图形、库、Python 分配器或工程评审 A/B 快照，不是整个进程的内存硬上限。单路/六路往返后的工作集可能保留一部分已申请内存，不能要求任务管理器每次立即回到刚启动值。

## 实测口径

在本机 Windows、Python 3.13.6、同一 1400×900 测试窗口、独立新进程下采样。默认设计为原 40W CCM 反激；六路工况使用 30/12/5/3.3/24/15 V、20/8/4/2/4/2 W，矩阵耦合关闭。浏览功率级、器件、磁件、电容、环路、效率、拓扑各两遍，回到拓扑页测量。窗口由测试创建，未读取或关闭用户现有窗口。

| 场景/指标 | 优化前 | 优化后 |
|---|---:|---:|
| 默认启动稳定后，工作集 RSS | 264 MiB | 154 MiB |
| 默认启动稳定后，线程数 | 41 | 8 |
| 六路浏览主要页面后，工作集 RSS | 497 MiB | 267 MiB |
| 六路浏览主要页面后，Windows 私有提交量 | 1458 MiB | 264 MiB |
| 六路浏览主要页面后，存活 TkAgg 画布 | 30 | 12 |

工作集 RSS 表示当时驻留物理内存；Windows 私有提交量是另一指标，不能把优化前的约 1.4 GiB 说成实际占用的物理内存。数字取整，属同机诊断，不是其他电脑的性能承诺。原始测量保存在开发目录 `_tmp_resource_qa/`。这些是源码新进程数据，不等同于 EXE 冷磁盘启动测量。

最终六路测试中，首次进入功率级页由约 3.17 s 变为 0.64 s，电容页由约 2.09 s 变为 0.45 s。每次包含约 0.2 s 的稳定等待，故不是纯绘图耗时；后台负载也会影响结果。首次环路页反而需要额外加载时间（本轮约 2.05 s），这是将启动开销移到实际使用时的取舍；重复切页也可能因图像缓冲重建比过去稍慢。没有证据表明原空闲 CPU 占用异常，本版不承诺一个固定 CPU 百分比。

## 不变的内容与边界

- 未降低采样点数、矩阵求解容差、绕制几何精度或报告图片分辨率，未改变电气公式和默认参数。计算说明 Word 没有因资源优化而修改公式。
- Word 使用独立图形生成，不依赖屏幕上是否已滚动到某一路；隐藏/释放 GUI 缓冲不省略报告内容。
- 未完成环路加载/计算前，相关检查为待算或待复核，不默认通过。进入环路/工程评审补齐当前设计检查；API 与完整报告保持完整计算。
- 多路两两耦合周期稳态仍可能较慢。输入防抖、单数值工作线程、最新任务覆盖和协作式取消继续生效，改善可交互性不等于所有物理求解瞬间完成。
- 导出、库内部单次调用和复杂绘图仍可能有短暂主线程操作；本次并非所有功能彻底异步化。

## 可选线程覆盖

一般无需设置。如需在专用计算机上对比，可在启动前设置进程环境变量 `POWER_DESIGN_NUM_THREADS` 为 1–32 的整数；默认 1，非法值回到 1。直接设置的 `OPENBLAS_NUM_THREADS`、`OMP_NUM_THREADS`、`MKL_NUM_THREADS` 等库环境变量优先保留。更大线程数不保证更快，且可能增加提交量；不建议为此修改系统级环境。

嵌入已有 Python 进程且 NumPy 已加载时，启动默认不能追溯收回已经创建的原生线程池；请以全新进程测试。
